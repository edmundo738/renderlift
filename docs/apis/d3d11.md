# D3D11 backend — integration plan (includes D3D10 notes)

**Priority: first.** Target lab: GTA V on Intel UHD 620 @ 1366×768.
GTA V (PC, DX11 default) + the entire D3D10/11 DXGI family share this model.

## Presentation model

D3D11 presents through a **DXGI swap chain**: `IDXGISwapChain::Present` and
`ResizeBuffers` are the natural integration anchors. D3D10 uses the same
family, so the backend's DXGI plumbing is shared; device-side interception
differs only in interface IDs.

## Planned hook targets (module contract)

| Target | Why |
|---|---|
| `IDXGISwapChain::Present` | frame boundary; reconstruction dispatch just before it |
| `IDXGISwapChain::ResizeBuffers` | keep redirection consistent across resolution changes |
| `ID3D11Device::CreateTexture2D` | **internal-resolution steering**: swap scene-sized textures for internal-res ones |
| `ID3D11Device::CreateRenderTargetView` | observe/steer RTVs of scene targets |
| `ID3D11DeviceContext::RSSetViewports` | clamp scene viewports to internal res |
| `ID3D11DeviceContext::OMSetRenderTargets` | classify which pass is rendering (scene vs UI) |
| `ID3D11DeviceContext::Draw[Indexed]` | pass classification heuristics |

## The two rules (from the architecture overview)

1. **Steer, don't resize.** The 3D pipeline must really run at the internal
   resolution — lower RT dimensions, matching viewports — so vertex/texel/
   lighting/post-process cost genuinely drops. A Present-time bitmap stretch
   changes nothing but the output bitmap.
2. **UI at native res.** GTA V draws HUD onto the final chain; we leave that
   alone so text/minimap stay crisp. ALRR touches only the scene image,
   between post-processing and UI composition.

## Pass-splitting heuristic (first approach)

Per frame, track RTV bindings by size and binding order:

- RTVs matching the *internal* steering set → scene pass (3D + post).
- First RTV matching *display* size late in the frame → start of UI pass;
  run ALRR reconstruction of the scene texture into that target *before*
  replaying UI draws (or into the backbuffer via our own composite pass).

This will need a small per-profile config block (GTA V: known RT chain from
external render-doc captures — fill in during 0.2; see docs/research/).

## Shadow maps, depth, effects

They already render at their own sizes; steering applies only to
**display-resolution-derived** targets. Depth prepass and G-buffer chains must
stay proportional to the internal resolution (they scale with scene size), or
aliasing/becomes-wrong. Special cases logged per title in the compatibility
matrix.

### Install evidence protocol (RLCAP1 checkpoints)

Because the module is invoked on a fresh remote thread inside a live game,
the install contract is defensive and self-diagnosing:

- Exports carry the exact thread-proc shape (`HRESULT WINAPI fn(LPVOID)`),
  so a loader-side `CreateRemoteThread` is ABI-exact, not merely compatible.
- Before touching STL, globals, D3D11 or MinHook, install writes
  `RLCAP1 install cp=1` with plain `fopen/fputs/fclose` to a durable log.
  Path resolution: `RENDERLIFT_LOG` env → the DLL's own directory → cwd,
  with a `%TEMP%` fallback so evidence is never silently lost. The log
  never lands next to the game executable.
- Each externally-visible step bumps a phase checkpoint
  (`1 entered · 2 state · 3 log · 4 hook engine · 5 vtables · 50–55 probe
  sub-steps · 60+i per-hook · 70 enable · 80 armed`) that is both written
  to the log and readable by the SEH filter.
- The whole install runs under an SEH guard whose filter records
  `RLCAP1 seh phase=N code=0xXXXXXXXX addr=0x...` (the exact faulting
  address) and converts the exception into a coded HRESULT
  (`0xE<phase><exception-code low 24 bits>`). Failure is reported with full
  evidence — never swallowed; success still means fully armed.
- Ordinary failures return distinguishable HRESULTs
  (`0x8000A001` state alloc, `0x8000A002` log open, `0x8000A003` hook
  engine, `0x8000A010` vtables, `0x8000A020+i` hook slot i, `0x8000A030`
  enable).

## GPU-busy telemetry without driver counters (first lab)

Intel iGPU: no trivial in-process GPU% counter. First approximation:
CPU-time between `Present` calls vs. GPU-fence completion time on a small
`D3D11_QUERY_EVENT` + timestamp delta; plus frame-time EWMA. The dynamic
controller consumes `FrameSample{frameMs, gpuBusy, cpuBusy}` — the estimator
refinement is an isolated backend concern (src/profiling hosts the pieces).
